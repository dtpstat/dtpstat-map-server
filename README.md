# dtpstat-buslines

Интерактивная карта и рейтинг выделенных полос России. Версия 2 использует
Node.js/Express, PostgreSQL/PostGIS и загружает из API только геометрии,
пересекающие текущее видимое окно карты.

## Архитектура

- `src/server.js` — точка запуска и корректное завершение процесса.
- `src/config.js` — строгая проверка настроек из `.env`.
- `src/app.js` — Express, статические ресурсы, защитные заголовки и API.
- `src/db/` — пул PostgreSQL, список городов и пространственные запросы GeoJSON
  по bbox карты.
- `src/db/data-import-service.js` — атомарная замена геометрий из полного GeoJSON.
- `src/db/population-import-service.js` — независимое обновление населения.
- `src/db/osm-city-update-service.js` — полный снимок российских OSM
  `place=city/town` и их административных полигонов/bbox.
- `src/db/kml-update-service.js` — загрузка KML, привязка линий по пересечению с
  OSM-полигонами и атомарная замена полос.
- `src/db/recalculate-city-statistics.js` — единый PostGIS-пересчёт длин и рейтинга.
- `src/data/admin-task-manager.js` — общая single-task очередь всех операций
  обновления, отмена, накопительный журнал и хранение результата.
- `src/db/admin-task-success-repository.js` — постоянные отметки времени
  последнего успешного обновления каждого типа.
- `src/http/admin-websocket.js` — защищённая Basic Auth WebSocket-трансляция
  состояния и журнала admin-задачи.
- `admin/` — защищённая web-панель запуска, отмены и наблюдения за всеми
  операциями обновления.
- `db/migrations/` — версионируемая схема PostGIS.
- `scripts/migrate.js` — последовательные версионные миграции с checksum и advisory lock.
- `scripts/init-database.js` — создание роли, БД и PostGIS от имени `postgres`.
- `scripts/import-data.js` — проверяемый импорт исходных CSV и GeoJSON.
- `public/js/` — API-клиент, контроллер карты и единый компонент рейтинга.

Desktop и mobile используют один `tbody`, одно состояние сортировки и один набор
обработчиков. Различается только адаптивная CSS-раскладка: боковая панель на
desktop и карта с карточным рейтингом на mobile.

## Быстрый запуск

Требуются Node.js 20.19+ и PostgreSQL с доступным расширением PostGIS.

```bash
npm install
cp .env.example .env
```

Укажите в `.env` публичный токен Mapbox. Локальную базу можно запустить через
Docker Compose:

```bash
docker compose up -d database
npm run db:init
npm run db:migrate
npm run db:import
npm run dev
```

После запуска сервера один раз загрузите справочник и границы городов из OSM:

```bash
curl --fail-with-body \
  --user "$IMPORT_API_USERNAME:$IMPORT_API_PASSWORD" \
  --request POST \
  "http://localhost:3000/api/admin/update/cities?dryRun=false"
```

После этого приложение доступно по адресу `http://localhost:3000`, а панель
администрирования — по адресу `http://localhost:3000/admin/`. Браузер запросит
`IMPORT_API_USERNAME` и `IMPORT_API_PASSWORD`. Повторный OSM-запрос заменяет
снимок границ атомарно и не меняет линии полос.

Импорт геометрий обновляет атрибуты соответствующих `cities` и заменяет
`city_geometries`, после чего
отдельно загружает 71 запись в `city_populations`. В исходном снимке находятся
71 город и 872 именованные геометрии. Десять объектов исходного GeoJSON без
`short_name` не импортируются: это дублированные или не связанные с рейтингом
результаты старого пространственного объединения. Длины и рейтинг из исходных
полей не используются: их рассчитывает PostGIS.

## HTTP и HTTPS

HTTP включён по умолчанию. Для HTTPS задайте:

```dotenv
HTTPS_ENABLED=true
HTTPS_PORT=3443
HTTPS_KEY_PATH=./certificates/localhost-key.pem
HTTPS_CERT_PATH=./certificates/localhost-cert.pem
```

HTTP и HTTPS могут работать одновременно. Для режима только HTTPS установите
`HTTP_ENABLED=false`. Сертификат и ключ должны быть PEM-файлами, читаемыми
процессом Node.js.

## Схема данных

Команда `db:init` от имени `postgres` создаёт прикладную роль, БД и подключает
PostGIS. Затем `V001__base_schema.sql` от имени прикладной роли создаёт или
подхватывает схему `buslanes` и исходные таблицы геометрий. Миграция
`V002__population_statistics.sql` без удаления строк выносит население в
отдельную таблицу. `V003` добавляет журнал KML-обновлений, `V004` переносит
границы городов в независимый OSM-справочник, `V005` разделяет OSM-объект и
необязательную рейтинговую запись города, `V006` добавляет в журнал размер и
число последовательных OSM-пакетов, а `V007` сохраняет последнюю успешную
реальную admin-операцию каждого типа:

- `cities`: название, суммарная длина полос, пересчитанный рейтинг, категория и
  дополнительные атрибуты;
- `city_populations`: отдельный текущий снимок населения, дата данных, источник
  и дополнительные атрибуты;
- `city_geometries`: точный `boundary_id`, необязательный `city_id`, число
  полос, длины, исходные свойства и `LineString`/`MultiLineString` в SRID 4326.
- `city_boundaries`: самостоятельный OSM `way/relation`, `place_type`, имя,
  теги, собранный `MultiPolygon` и bbox в SRID 4326. Одинаковые имена разрешены;
  связь с рейтинговым `city_id` необязательна.
- `geometry_update_runs`, `osm_city_update_runs`: журналы успешных замен с
  checksum и объёмом скачанных данных.
- `admin_task_successes`: последняя успешная операция по каждому типу задачи;
  сохраняется между перезапусками сервера. Проверочные `dryRun` в неё не
  записываются.

Для доступа по городу создан B-tree индекс, для пространственных запросов —
GiST. Версия схемы хранится в `public.buslanes_schema_versions`. Файлы имеют
строгие последовательные имена `V001__*.sql`, `V002__*.sql` без пропусков;
каждая версия выполняется в отдельной транзакции. Повторный запуск безопасен,
а изменение уже применённого SQL обнаруживается по SHA-256.
Применённые файлы не редактируются: каждое следующее изменение схемы добавляется
новым последовательным файлом, например `V008__description.sql`.

Старую `public.schema_migrations`, если она уже существует, мигратор не удаляет
и не изменяет. Идемпотентная `V001` распознаёт уже созданную legacy-схему,
поэтому наличие `buslanes`, `cities` или `city_geometries` не считается ошибкой.
`V002` сначала копирует существующее население с `ON CONFLICT DO NOTHING` и
только затем меняет структуру и пересчитывает показатели в той же транзакции.

## Двухступенчатая инициализация БД

Первая ступень запускается отдельно:

```bash
npm run db:init
```

Только эта команда читает `POSTGRES_ADMIN_*` и подключается как `postgres`. Она:

1. проверяет наличие `DATABASE_ROLE`;
2. создаёт роль либо меняет существующей роли пароль на
   `DATABASE_ROLE_PASSWORD`;
3. создаёт `DATABASE_NAME`, только если такой БД ещё нет;
4. назначает существующую или созданную БД роли `DATABASE_ROLE`;
5. от имени `postgres` подключает расширение PostGIS при его отсутствии;
6. назначает роли все пользовательские схемы, таблицы, последовательности,
   представления, пользовательские типы и функции внутри БД;
7. оставляет системные и принадлежащие расширениям объекты у их владельцев;
8. проверяет вход в целевую БД уже под прикладной ролью.

Повторный `db:init` не пересоздаёт БД и не удаляет данные. Он синхронизирует
пароль роли и владельцев прикладных объектов с текущими значениями `.env`.
Объекты PostGIS не переоформляются: они остаются под управлением расширения.

Вторая ступень выполняется только прикладной ролью:

```bash
npm run db:migrate
npm run db:import
npm run dev
```

Эти процессы вообще не читают `POSTGRES_ADMIN_PASSWORD`; для подключения они
используют исключительно `DATABASE_ROLE` и `DATABASE_ROLE_PASSWORD`.

## API

- `GET /api/health` — доступность приложения и базы.
- `GET /api/config` — только публичная конфигурация карты.
- `GET /api/cities` — города, рейтинг, категория, bbox и точка внутри OSM-полигона.
- `GET /api/geometries?bbox=west,south,east,north&center=lng,lat` — линии,
  пересекающие видимое окно, обрезанные по bbox, и `centerCityId` города под
  центром карты. Максимальный размах публичного bbox — 20° по каждой оси.
- `GET /api/cities/:cityId/geometries` — GeoJSON `FeatureCollection` выбранного
  города; оставлен для совместимости.
- `POST /api/admin/import` — фоновая полная замена линий и обновление атрибутов
  их городов из GeoJSON.
- `POST /api/admin/populations` — фоновое независимое обновление населения и
  рейтинга.
- `POST /api/admin/update/cities` — запускает фоновое обновление полного снимка
  российских OSM `place=city/town`; сразу возвращает `202` и ID задачи.
- `POST /api/admin/update` — фоновая загрузка указанных KML-слоёв и полная
  замена линий.
- `GET /api/admin/status` — текущая либо последняя завершённая admin-задача и
  постоянные `lastSuccessfulUpdates`; при отсутствии задачи возвращает
  `status: "idle"`.
- `GET /api/admin/status/:taskId` — состояние, накопительный журнал и результат
  конкретной текущей/последней задачи.
- `POST /api/admin/cancel` — запрос отмены активной задачи.
- `POST /api/admin/cancel/:taskId` — запрос отмены задачи с явным ID.
- `WS /api/admin/ws` — начальный снимок и события журнала/состояния в реальном
  времени.
- `GET /admin/` — web-панель всех перечисленных операций.

Все `/api/admin/*` и `/admin/` защищены одной парой Basic Auth из ENV. WebSocket
проверяет тот же заголовок `Authorization` ещё при upgrade-запросе.

В панели настройки операций находятся во вкладках слева, а состояние, журнал и
результат всегда отображаются справа. При активной задаче панель автоматически
выбирает соответствующую вкладку, блокирует переключение и заменяет кнопку
запуска кнопкой отмены. После перезагрузки страницы состояние восстанавливается
через `/api/admin/status`, затем обновляется событиями WebSocket. Сообщения об
успехе, ошибке и отмене принадлежат своей вкладке и не переходят на другую
операцию. В каждой
вкладке всегда показано время последнего успешного реального обновления этого
типа; проверочный `dryRun`, отмена и ошибка отметку не меняют.

Последовательность клиента: конфигурация карты → список городов и их маркеры →
первый крупный город → `fitBounds` по его OSM-границам → GeoJSON текущего
видимого окна. На zoom `0–7` линии не запрашиваются: показываются подписанные
маркеры городов с предоставленной иконкой. Начиная с zoom `8`, каждый `moveend`
отменяет незавершённый предыдущий запрос и загружает линии нового bbox. Город,
чей OSM-полигон находится под центром карты, подсвечивается в единой таблице;
при необходимости автоматически выбирается его категория и строка прокручивается
в видимую область. Клик по строке не загружает город отдельно — только выполняет
`fitBounds`, после чего срабатывает тот же viewport-поток. Клик по маркеру на
малом зуме выполняет ровно тот же выбор города, подсветку строки и `fitBounds`.

### Обновление данных через API

#### Общий жизненный цикл admin-задач

Каждый изменяющий `POST /api/admin/*` только принимает данные, ставит операцию
на выполнение и сразу отвечает `HTTP 202`:

```json
{
  "status": "accepted",
  "taskId": "31f0e2c5-2fd1-4c57-a82a-891571187905",
  "task": {
    "id": "31f0e2c5-2fd1-4c57-a82a-891571187905",
    "type": "osm-city-update",
    "status": "queued",
    "cancellable": true,
    "statusURL": "/api/admin/status/31f0e2c5-2fd1-4c57-a82a-891571187905"
  }
}
```

Сервер исполняет ровно одну задачу любого типа одновременно. Пока она активна,
любой другой изменяющий admin-запрос немедленно получает `HTTP 409`, `taskId` и
`statusURL` уже выполняемой задачи. Состояния: `queued`, `running`,
`cancelling`, `cancelled`, `succeeded`, `failed`.

```bash
curl --fail-with-body \
  --user "$IMPORT_API_USERNAME:$IMPORT_API_PASSWORD" \
  https://example.org/api/admin/status/31f0e2c5-2fd1-4c57-a82a-891571187905

curl --fail-with-body \
  --user "$IMPORT_API_USERNAME:$IMPORT_API_PASSWORD" \
  --request POST \
  https://example.org/api/admin/cancel/31f0e2c5-2fd1-4c57-a82a-891571187905
```

Отмена кооперативная: сетевые запросы прерываются сразу, а сервисы проверяют
сигнал между этапами и выполняют `ROLLBACK`. На короткой стадии атомарного
`COMMIT` поле `cancellable` становится `false`; отмена в этот момент возвращает
`409`, чтобы не сообщать об отмене уже публикуемых данных.

Полный журнал и итог последней задачи остаются доступны после её завершения и
очищаются только при принятии следующей задачи. Хранилище процесса не
персистентно: после перезапуска сервера статус и журнал пусты. Отметки последних
успешных обновлений хранятся в PostgreSQL и остаются доступны всегда. Для
наблюдения без опроса подключайтесь к `ws(s)://<host>/api/admin/ws`: сначала
приходит событие `snapshot`, затем `log`, `task` и `success`.

При применении `V007` история KML, OSM-городов и населения восстанавливается из
существующих журналов. Для старых GeoJSON-импортов достоверного общего журнала
нет, поэтому их отметка появится после первого следующего успешного импорта.

Endpoint геометрий принимает полный `FeatureCollection` в формате `application/geo+json`
или `application/json`:

```bash
curl --fail-with-body \
  --user "$IMPORT_API_USERNAME:$IMPORT_API_PASSWORD" \
  --header "Content-Type: application/geo+json" \
  --data-binary @bus-lanes.geojson \
  https://example.org/api/admin/import
```

Basic Auth необходимо использовать через HTTPS либо через доверенный HTTPS
reverse proxy. Проверка авторизации всех закрытых endpoint выполняется до
чтения тела.

Загрузка считается полным снимком линий: все прежние линии заменяются,
существующие города сохраняют свои ID, а OSM-города и их границы не удаляются.
В одной транзакции сервер:

1. проверяет структуру, названия городов, координаты WGS84 и атрибуты объектов;
2. принимает `properties.lanes=1` как одностороннюю и `lanes=2` как
   двустороннюю полосу;
3. группирует именованные объекты по `properties.short_name` и заменяет
   связанные геометрии;
4. вычисляет метры как `ST_Length(geom::geography)` для WGS84/EPSG:4326;
5. в конце суммирует `длина × lanes` и обновляет рейтинг города.

Геометрии и bbox городов этот endpoint не вычисляет и не изменяет.

Поля источника `population`, `length` и `lanes_length` сохраняются в JSONB для
трассировки, но не участвуют в расчётах.

При ошибке выполняется rollback. Параллельные импорты сериализуются advisory
lock. Объекты без `short_name` пропускаются так же, как при CLI-импорте.
После завершения эти количества и время обновления находятся в `task.result`.

### Обновление населения

Население обновляется независимо, одной или несколькими записями. Города,
которые не указаны в запросе, остаются без изменений:

```json
{
  "asOf": "2026-01-01",
  "source": "Росстат",
  "populations": [
    {
      "name": "Казань",
      "population": 1300000,
      "attributes": { "note": "предварительные данные" }
    }
  ]
}
```

```bash
curl --fail-with-body \
  --user "$IMPORT_API_USERNAME:$IMPORT_API_PASSWORD" \
  --header "Content-Type: application/json" \
  --data-binary @populations.json \
  https://example.org/api/admin/populations
```

`asOf`, `source` и `attributes` необязательны. Названия должны точно совпадать с
`cities.name`; неизвестный или повторяющийся город отклоняет весь запрос. После
UPSERT сервер в той же транзакции заново рассчитывает для городов категорию и
метры выделенных полос на 1000 жителей.

### Обновление городов из OSM

`POST /api/admin/update/cities` выполняет фиксированные Overpass-запросы: только
территория Российской Федерации, только объекты `way` и `relation` с
`place=city` либо `place=town` и непустым `name`. Порог населения намеренно не
применяется. Одинаковые названия в разных регионах сохраняются как разные
OSM-объекты и не объединяются по строке имени.

Тело необязательно; без него используются настройки `.env`. Разрешённое
переопределение URL имеет строгую структуру:

```json
{"URL":"https://overpass-api.de/api/interpreter"}
```

Параметры `dryRun`, `timeoutMs`, `queryTimeoutSeconds`, `maxBytes` и `batchSize`
можно передать query-параметрами. Лимиты времени и общего объёма можно только
уменьшить относительно ENV, а `batchSize` не может превысить
`OSM_CITY_UPDATE_MAX_BATCH_SIZE`. Например:

```bash
curl --fail-with-body \
  --user "$IMPORT_API_USERNAME:$IMPORT_API_PASSWORD" \
  --request POST \
  "https://example.org/api/admin/update/cities?dryRun=true&timeoutMs=120000&batchSize=25"
```

POST не ждёт Overpass и сразу отвечает общим `HTTP 202`-контрактом задачи.
Прогресс индексных частей и пакетов добавляется в `task.log`; при завершении
появляется `task.result` или `task.error`. Глобальная блокировка не позволяет
параллельно запустить ни OSM, ни KML, ни GeoJSON, ни обновление населения.

Сначала сервер четырьмя небольшими последовательными запросами получает ID для
`city/way`, `city/relation`, `town/way` и `town/relation`, проверяя общую
уникальность. Затем он строго последовательно запрашивает по `N=batchSize`
объектов, проверяет совпадение ответа с индексом и сразу собирает во временной
PostGIS-таблице `MultiPolygon` через `ST_Node`, `ST_BuildArea` и `ST_MakeValid`.
После загрузки всех пакетов проверяются их количество, валидность и bbox. Только
после этого начинается короткая транзакция, которая заменяет `city_boundaries`
и восстанавливает связи существующих линий по `osm_type/osm_id`.

Ошибка или таймаут любого пакета удаляет лишь временную таблицу при закрытии
соединения: опубликованные границы, население и линии остаются неизменными.
Параметр `dryRun=true` дополнительно выполняет финальную замену с `ROLLBACK`.
Рейтинговый `city_id` связывается по прежнему OSM-объекту либо по единственному
точному совпадению имени. Успешный запуск записывает `batch_size` и
`batch_count` в `osm_city_update_runs`.

Незавершённая staging-загрузка при ошибке, отмене или остановке процесса не
публикуется.

### Обновление KML-линий

`POST /api/admin/update` без тела использует `KML_UPDATE_SOURCES_JSON`. Тело
запроса полностью заменяет ENV-список и имеет строгую структуру:

```json
[
  {
    "URL": "https://www.google.com/maps/d/viewer?mid=...",
    "layers": [
      {"name": "Односторонние", "multiple": 1},
      {"name": "Двусторонние", "multiple": 2}
    ]
  }
]
```

Перед KML-обновлением обязательно загрузить OSM-границы. Bbox/GiST используется
только как быстрый предфильтр. Принадлежность определяется положительной длиной
пересечения линии с настоящим `MultiPolygon`; при нескольких кандидатах
выбирается максимальная длина пересечения. Затем учитываются связь с рейтинговым
городом, меньшая площадь полигона и стабильный OSM ID. Старые линии заменяются
только после успешного скачивания, XML-разбора и пространственной проверки всех
источников.

Параметр `cityBufferMeters` расширяет каждый полигон геодезическим буфером в
метрах. Он не может превышать `KML_UPDATE_CITY_BUFFER_MAX_METERS`. Нулевой буфер
даёт строгое пересечение; 500–1000 м могут подобрать пограничные линии, но
увеличивают число объектов с несколькими кандидатами.
`multiple=1` считает геодезическую длину один раз, `multiple=2` — дважды.
Физическая длина всегда вычисляется PostGIS как
`ST_Length(geom::geography)` для WGS84/EPSG:4326.

```bash
curl --fail-with-body \
  --user "$IMPORT_API_USERNAME:$IMPORT_API_PASSWORD" \
  --header "Content-Type: application/json" \
  --data-binary @kml-update.json \
  "https://example.org/api/admin/update?dryRun=true&cityBufferMeters=0"
```

```bash
npm run check
```

Команда запускает ESLint и тесты конфигурации, обоих защищённых API,
