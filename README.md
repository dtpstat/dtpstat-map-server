# dtpstat-map-server

Node.js/Express + PostgreSQL/PostGIS сервер интерактивной карты линейных объектов. Репозиторий вырос из проекта карты выделенных полос, но runtime больше не привязан к имени исходного проекта: один код можно разворачивать несколькими независимыми экземплярами с разными БД, схемами, портами, данными, расчётами и публичным названием.

## Основные возможности

- публичная карта Mapbox с viewport-загрузкой линий; сервер выбирает полные геометрии по окну, увеличенному до 120% ширины и высоты, чтобы линии не исчезали на границе экрана;
- настраиваемый рейтинг городов: колонки, расчётные метрики, ссылки между метриками, агрегаты, группировки, арифметика, явные приоритеты операций и направление рейтинга;
- агрегаты геометрий `SUM`, `AVG`, `MEDIAN`, `MIN`, `MAX`, `COUNT` там, где они допустимы;
- поля уровня города, включая население и геодезическую площадь OSM-границы в м²;
- материализованные расчётные значения `CITY_REPORT_VALUES`, которые пересчитываются после обновления данных, а не на каждый публичный запрос;
- независимо настраиваемый статический публичный CSV;
- условное форматирование числовых колонок публичной таблицы по диапазонам значений;
- справочник бизнес-типов линий с отдельными `NAME`, `TITLE`, цветом, стилем и толщиной;
- загрузка городов/границ из OSM Overpass;
- импорт линий из KML / Google My Maps;
- перенос городов, линий и населения между экземплярами через admin API;
- переносимый KML с полным словарём типов линий;
- защищённая Basic Auth админка с единственной выполняемой admin-задачей, журналом, dry-run и WebSocket-статусом;
- статические публичные GeoJSON/CSV snapshots и отдельные динамические admin-экспорты;
- HTTP и/или HTTPS;
- структурированные служебные логи и graceful shutdown.

Требуются Node.js `20.19+` и PostgreSQL с доступным PostGIS.

## Быстрый запуск

```bash
npm install
cp .env.example .env
```

Заполните как минимум параметры PostgreSQL, Basic Auth и `MAPBOX_ACCESS_TOKEN`, затем:

```bash
npm run db:init
npm run db:migrate
npm start
```

`db:init` создаёт/обновляет прикладную роль и БД и включает PostGIS. `db:migrate` применяет неизменяемую последовательность миграций V001…V015.

На полностью пустой БД сервер и админка работоспособны. Публичная страница показывает нормальное состояние `Данные пока не загружены`, а не ошибку. Данные можно наполнить через `/admin/`.

Для локальной БД можно использовать `compose.yaml`:

```bash
docker compose up -d database
npm run db:init
npm run db:migrate
npm start
```

## Независимые экземпляры

Рекомендуемая модель: **один экземпляр приложения — одна PostgreSQL database**.

`DATABASE_SCHEMA` одновременно является SQL-схемой и техническим namespace экземпляра. По умолчанию для совместимости используется `buslanes`. Настройка влияет на:

- `search_path`;
- PostgreSQL `application_name`;
- advisory locks;
- таблицу истории миграций;
- служебный namespace обновлений;
- default User-Agent OSM updater.

Например второй экземпляр на том же сервере:

```dotenv
DATABASE_NAME=tramlanes
DATABASE_ROLE=tramlanes_app
DATABASE_SCHEMA=tramlanes
HTTPS_ENABLED=true
HTTPS_PORT=3002
```

Первый и второй экземпляры должны использовать разные HTTP/HTTPS-порты. Если они подключены к одному PostgreSQL server, сам `DATABASE_PORT` может совпадать.

Подробнее: [docs/deployment.md](docs/deployment.md).

## Схема, миграции и индексы

Прикладные таблицы находятся в `<DATABASE_SCHEMA>`:

- `cities` — города и legacy/cache статистика, используемая в том числе для категорий;
- `city_populations` — население и метаданные источника;
- `city_boundaries` — OSM city/town и их Polygon/MultiPolygon;
- `city_geometries` — линии, связанные с OSM-границей и бизнес-типом;
- `line_types` — словарь бизнес-типов и визуальных настроек;
- `project_settings` — название проекта, keywords, footer и ID аналитики;
- `report_config` — безопасное декларативное описание метрик, публичной таблицы, CSV и рейтинга;
- `city_report_values` — подготовленные scalar-метрики и rank для каждого города;
- журналы обновлений и `admin_task_successes`.

История миграций хранится в:

```text
<DATABASE_SCHEMA>.schema_versions
```

Для старых установок мигратор умеет импортировать историю из legacy `public.buslanes_schema_versions`. Файлы миграций после применения **не редактируются**. Исторические SQL-файлы содержат имя `BUSLANES`; migration runner подставляет выбранный `DATABASE_SCHEMA` только перед исполнением, а checksum рассчитывает по оригинальному неизменённому файлу.

`V015__index_audit.sql` фиксирует результат отдельного аудита индексов. Пространственные выборки уже покрыты GiST-индексами `CITY_GEOMETRIES.GEOM` и `CITY_BOUNDARIES.GEOM/BOUNDS`; FK/identity-поиски покрыты PK/UNIQUE/B-tree индексами. Для горячей таблицы линий старый индекс только по `CITY_ID` заменяется на `(CITY_ID, LINE_TYPE_ID)`: левый префикс сохраняет city-only доступ и одновременно лучше соответствует отчётным joins/grouping по типу линии. Для singleton и append-only audit-таблиц лишние индексы намеренно не создаются.

Следующее изменение схемы должно быть новой миграцией **V016+**. Приоритеты операций, ссылки между метриками, площадь города, медиана и условное форматирование хранятся/описываются существующей JSONB-моделью и дополнительных колонок БД не требуют.

Подробно об индексах: [docs/database-indexes.md](docs/database-indexes.md).

## Конструктор расчётов

В `/admin/` есть отдельная вкладка **«Расчёты»**, внутри которой четыре под-вкладки:

1. **Метрики** — scalar-метрики для каждого города;
2. **Публичная таблица** — состав, порядок, формат чисел и условное оформление;
3. **CSV** — независимый состав статической выгрузки;
4. **Рейтинг** — метрика места и направление `больше — выше` / `меньше — выше`.

Сохранение остаётся единым: конфигурация валидируется, затем `CITY_REPORT_VALUES` пересчитывается транзакционно, после чего обновляются публичные snapshots.

В конструкторе **нет произвольного SQL**. Технические поля, другие метрики, агрегаты, группировки, арифметические операции, уровни приоритета, константы, масштабы и точность доступны только через server-owned каталоги и контролы. Имена SQL-таблиц/колонок из браузера в запрос не подставляются; пользовательские значения передаются параметрами PostgreSQL.

Текущая версия поддерживает:

- поля города: население и площадь OSM-границы `city.area_m2` в квадратных метрах;
- поля геометрий: физическая длина, длина с коэффициентом/полосами, значение `lanes`, количество геометрий;
- агрегаты: `SUM`, `AVG`, `MEDIAN`, `MIN`, `MAX`, `COUNT` там, где они допустимы;
- медиану через PostgreSQL `PERCENTILE_CONT(0.5) WITHIN GROUP`;
- условную группировку/выбор одной группы по `LINE_TYPES.NAME`;
- ссылки одной метрики на другую как на исходное значение или операнд;
- автоматический топологический порядок materialization и запрет циклических зависимостей;
- арифметику: `+`, `−`, `×`, `÷`, процент;
- уровни приоритета `1…12`: больший уровень выполняется раньше, одинаковый — слева направо;
- преобразование выражения в обратную польскую запись перед компиляцией SQL;
- read-only preview фактических скобок и ОПЗ непосредственно в админке;
- перемещение метрик, арифметических операций, колонок и правил условного форматирования кнопками `↑/↓`;
- фиксированный каталог безопасных констант;
- раздельный scale/precision для каждой колонки таблицы и CSV.

Например базовые трамвайные показатели можно разделить:

```text
network_length_m   = SUM(geometry.length_m)
separated_length_m = SUM(geometry.length_m WHERE LINE_TYPES.NAME = «Обособленные»)
separation_ratio   = metric(separated_length_m) / metric(network_length_m)
```

А плотность населения можно собрать как:

```text
population      = city.population
city_area_m2    = city.area_m2
people_per_km2  = metric(population) / metric(city_area_m2) × 1000000
```

Для площади используется `ST_Area(CITY_BOUNDARIES.GEOM::geography)`, поэтому результат задаётся в м²; при отсутствии границы значение `NULL`.

Чтобы получить `(A + B) × C`, операции `+` задаётся более высокий уровень, чем `×`. Для `A + (B × C)` — наоборот. Старые настройки без `priority` автоматически получают уровень `1`, поэтому сохраняют прежнее вычисление строго слева направо.

### Условное форматирование

Для числовых колонок **места** и **метрик** публичной таблицы можно создать до восьми правил диапазонов. Для каждого правила задаются:

- нижняя и/или верхняя граница, обе включительно;
- жирный;
- курсив;
- подчёркивание;
- зачёркивание;
- цвет текста;
- размер `−2`, `−1`, обычный, `+1`, `+2` пункта.

Для metric-колонки диапазон проверяется **после применения `scale`**, то есть в тех единицах, которые видит пользователь. Пустая граница означает бесконечный край диапазона. Если диапазоны пересекаются, применяется первое правило сверху; порядок правил меняется `↑/↓`. Форматирование относится только к HTML-таблице и не влияет на числовые значения, сортировку, materialization или CSV.

`CITY_REPORT_VALUES` пересчитывается:

- при старте приложения;
- после успешного изменения линий;
- после импорта/обновления границ городов;
- после обновления населения;
- сразу при сохранении настройки расчётов.

Публичный `/api/cities` возвращает подготовленный объект `metrics`, а `/api/report-config` — описание отображаемых колонок, включая безопасные правила форматирования. Поэтому публичный посетитель не запускает агрегирующий PostGIS/SQL-расчёт.

Миграция V014 создаёт default-конфигурацию, воспроизводящую прежнюю таблицу выделенных полос:

```text
№ | город | длина ВП (км) | жители (тыс.) | ВП (м/1000 чел.)
```

Для проекта трамвайных систем можно без изменения кода собрать:

```text
№ | город | доля обособления | длина сети (км) | население (тыс.чел)
```

Подробно: [docs/report-config.md](docs/report-config.md).

## Viewport линий

Клиент отправляет серверу фактический bbox видимого окна. После обычной API-валидации сервер увеличивает его ширину и высоту на **20% в целом**: добавляется по 10% исходного размера с каждой стороны. Координаты ограничиваются WGS84 диапазоном `[-180..180] / [-90..90]`.

SQL использует оба пространственных предиката:

```text
GEOM && padded_bbox
ST_Intersects(GEOM, padded_bbox)
```

Первый использует GiST bbox-index, второй подтверждает реальное пересечение. Геометрия в ответе **не обрезается** через `ST_Intersection`: если линия хотя бы частично пересекает расширенное окно, клиент получает её целиком. Это устраняет визуальное исчезновение линий непосредственно у края движущегося viewport и одновременно оставляет запас для следующего небольшого pan.

## Модель типов линий

Актуальная модель `LINE_TYPES`:

| Поле | Назначение |
| --- | --- |
| `ID` | локальный PK |
| `CODE` | числовой код, генерируется БД, пользователь его не назначает и не редактирует |
| `NAME` | source/import identity; уникален без учёта регистра и внешних пробелов |
| `TITLE` | человекочитаемая подпись легенды |
| `COLOR` | цвет |
| `LINE_STYLE` | `solid`, `dashed`, `dotted` |
| `WIDTH` | толщина |

`CITY_GEOMETRIES.LINE_TYPE_ID` хранит только локальный FK на `LINE_TYPES.ID`.

`NAME` и `TITLE` имеют разные роли: импорт сопоставляет типы по нормализованному `NAME`; `TITLE` используется только для представления. `CODE` является компактной числовой ссылкой в переносимых форматах, но его значение не обязано совпадать между двумя БД.

На публичной карте легенда показывает только типы, у которых реально есть геометрии. Если используется не более одного типа, отдельная легенда не рисуется.

## Обновление данных

Основные операции доступны в `/admin/` и через защищённый `/api/admin/*`.

### Города

Можно загрузить актуальный список `place=city/town` и границы из OSM Overpass либо перенести готовый GeoJSON snapshot. Импорт большого GeoJSON городов сначала валидирует весь файл, затем загружает геометрии во временную таблицу пакетами по 50 объектов, чтобы не отправлять весь большой FeatureCollection одним PostgreSQL JSONB-параметром.

### Линии

Поддерживаются:

- внешний KML / Google My Maps;
- переносимый GeoJSON;
- переносимый KML.

В конфигурации внешнего KML поле `type` содержит **`LINE_TYPES.NAME`**, а не числовой `CODE`. Сопоставление выполняется без учёта регистра и внешних пробелов. Если такого `NAME` ещё нет, тип создаётся автоматически: `CODE` назначает БД, начальный `TITLE = NAME`.

### Население

Население импортируется отдельным JSON snapshot и после успешной фиксации запускает пересчёт зависимой статистики и материализованного отчёта.

Все длительные mutating-операции проходят через единый single-task guard. `dryRun` выполняет проверку без фиксации данных и не обновляет отметку последнего успешного обновления.

Форматы переноса: [docs/data-transfer.md](docs/data-transfer.md) и [docs/kml-transfer.md](docs/kml-transfer.md).

## Публичные downloads и admin exports

Публичные ссылки:

```text
/bus-lanes.geojson
/bus-lanes.csv
```

не выполняют тяжёлый SQL при каждом скачивании. Сервер материализует обычные файлы в:

```text
var/public-downloads/
```

Snapshot строится при старте и после успешного реального изменения данных. Файлы заменяются атомарно. `dryRun` их не пересобирает.

Публичный GeoJSON намеренно содержит только данные, полезные потребителю карты/данных, и **не содержит** `_dtpstat`, словарь стилей, `TITLE/COLOR/STYLE/WIDTH` и другую служебную информацию для round-trip.

Публичный CSV строится из `CITY_REPORT_VALUES` и собственного списка колонок `REPORT_CONFIG.CSV_COLUMNS`. Это позволяет, например, выводить в HTML долю обособления и длину сети, а в CSV дополнительно добавить категорию города и bounding box либо использовать другое масштабирование/точность.

Admin-экспорты остаются динамическими и полными:

```text
GET /api/admin/export/cities
GET /api/admin/export/lines
GET /api/admin/export/lines.kml
GET /api/admin/export/populations
```

Именно admin-форматы следует использовать для переноса/backup между экземплярами.

## Служебные логи

Сервер пишет grep-friendly события с единым префиксом:

```text
[service] startup
[service] database.health:start
[service] database.health:ok
[service] city-report.refresh:start
[service] city-report.refresh:ok
[service] public-downloads.refresh:start
[service] public-downloads.refresh:ok
[service] postgres.connection:error
[service] shutdown:start
[service] shutdown:ok
```

Для операций указывается `durationMs`, а для ошибок — безопасные `name`, `code`, `message` и технический контекст без паролей/токенов.

Неожиданная потеря отдельного PostgreSQL connection логируется через `Pool#error` / `Client#error` и не должна превращаться в необработанный EventEmitter error, завершающий весь Node-процесс. SQL-ошибка конкретного запроса по-прежнему возвращается вызывающей операции.

## Production / PM2

Для PM2 лучше запускать Node напрямую, без дополнительного npm wrapper:

```bash
pm2 start src/server.js --name tramlanes
pm2 save
```

Так имя процесса принадлежит конкретному экземпляру, а npm metadata остаётся нейтральной (`dtpstat-map-server`).

Для production используйте HTTPS, длинный Basic Auth пароль и отдельную непривилегированную PostgreSQL роль. `POSTGRES_ADMIN_*` нужны только `npm run db:init`.

## Проверка

```bash
npm run check
```

Команда запускает ESLint и весь набор Node tests.

После изменения `.env` или обновления deployment под PM2:

```bash
pm2 restart <instance-name> --update-env
```

## Bootstrap из исторического snapshot

Корневые `bus-lanes.geojson` и `bus-lanes.csv` сохранены только как исходный bootstrap snapshot для команды:

```bash
npm run db:import
```

Они **не** обслуживают публичные `/bus-lanes.geojson` и `/bus-lanes.csv`; публичные файлы всегда строятся из текущей БД в `var/public-downloads/`.
