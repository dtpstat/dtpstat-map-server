# Конструктор расчётов и публичного отчёта

Начиная с миграции `V014`, набор колонок публичного рейтинга и CSV не зашит в код под конкретный транспортный проект. Настройка находится в отдельной вкладке **«Расчёты»** административной панели.

Цель механизма — дать возможность собирать типовые бизнес-показатели без произвольного SQL. Администратор выбирает поля, агрегаты, другие метрики, группировки, арифметические операции, приоритет вычисления и форматирование только из списков, которые публикует сервер.

## Модель хранения

`REPORT_CONFIG` — singleton-конфигурация отчёта:

- `METRICS` — декларативные определения scalar-метрик;
- `TABLE_COLUMNS` — колонки публичной таблицы;
- `CSV_COLUMNS` — независимые колонки статического CSV;
- `RANK_METRIC_KEY` — метрика, формирующая место города;
- `RANK_DIRECTION` — `asc` или `desc`;
- `UPDATED_AT`.

`CITY_REPORT_VALUES` — материализованный результат для каждого города:

- `CITY_ID`;
- `VALUES` — JSONB-словарь `{ metricKey: value }`;
- `RANK_VALUE`;
- `RANK`;
- `UPDATED_AT`.

Это намеренно обычная таблица, а не PostgreSQL `MATERIALIZED VIEW`: набор метрик динамический, поэтому фиксированные SQL-колонки представления были бы неудобны. Публичные запросы читают уже подготовленные значения и не выполняют вычисления заново для каждого посетителя.

Добавление приоритетов операций, ссылок между метриками, перестановки элементов конструктора и поля площади города не требует новой миграции: выражения и порядок метрик уже хранятся в `REPORT_CONFIG.METRICS` как JSONB, а площадь вычисляется из существующей `CITY_BOUNDARIES.GEOM` во время материализации отчёта.

## Когда происходит пересчёт

Полный `CITY_REPORT_VALUES` пересчитывается:

1. при старте сервера;
2. после успешного изменения линий;
3. после успешного обновления/импорта границ городов;
4. после обновления населения;
5. сразу при сохранении конфигурации во вкладке «Расчёты».

При обычных admin-import/update операциях сначала фиксируются исходные данные, затем пересчитывается отчёт, после чего атомарно обновляются статические `/bus-lanes.geojson` и `/bus-lanes.csv`.

При сохранении самой конфигурации запись `REPORT_CONFIG` и пересчёт `CITY_REPORT_VALUES` выполняются одной DB-транзакцией. После commit пересобираются публичные файлы.

## Разрешённые исходные поля

Конструктор предоставляет следующие логические поля:

| Поле в конструкторе | Значение |
| --- | --- |
| `city.population` | население города, человек |
| `city.area_m2` | площадь административной границы города, м² |
| `geometry.length_m` | физическая длина геометрии, м |
| `geometry.lane_length_m` | длина с учётом коэффициента/числа полос, м |
| `geometry.lanes` | коэффициент/число полос геометрии |
| `geometry.id` | идентификатор, используется для `COUNT` |

`city.area_m2` вычисляется сервером как геодезическая площадь OSM-границы:

```text
ST_Area(CITY_BOUNDARIES.GEOM::geography)
```

Результат — квадратные метры. Если граница для города отсутствует, значение площади будет `NULL`.

Логические имена являются частью server-owned каталога. Пользователь не вводит их вручную.

## Агрегаты

Для подходящих полей доступны только:

- `SUM`;
- `AVG`;
- `MIN`;
- `MAX`;
- `COUNT`.

Конкретный список зависит от выбранного поля. Например, `geometry.id` разрешает только `COUNT`. Поля уровня города (`population`, `area_m2`) используются как scalar и не требуют агрегатора.

## Группировка

Доступны:

- без группировки;
- по `LINE_TYPES.NAME`.

В отчёте всё равно должна получиться одна scalar-величина на город. Поэтому «по бизнес-типу» означает условный агрегат по **одной выбранной группе**. Сам `NAME` выбирается из текущего справочника типов линий.

Например:

```text
SUM(длина геометрии)
для бизнес-типа NAME = «Обособленные»
```

может служить метрикой `separated_length_m`.

## Ссылки одной метрики на другую

В качестве исходного значения метрики или правого операнда можно выбрать **«Другая метрика»**. Конкретная метрика выбирается только из dropdown; `metricKey` вручную не вводится.

Например вместо повторения одинаковых агрегатов можно собрать:

```text
network_length_m   = SUM(geometry.length_m)
separated_length_m = SUM(geometry.length_m WHERE LINE_TYPES.NAME = «Обособленные»)
separation_ratio   = metric(separated_length_m) / metric(network_length_m)
```

Или плотность населения:

```text
population    = city.population
city_area_m2  = city.area_m2
people_per_km2 = metric(population) / metric(city_area_m2) × 1000000
```

Сервер строит граф зависимостей и перед materialization выполняет метрики в топологическом порядке. Поэтому физический порядок карточек в админке не обязан совпадать с порядком вычисления.

Карточки метрик можно переставлять кнопками `↑/↓`. Этот порядок сохраняется как пользовательский порядок конфигурации и используется в самой админке и в выпадающих списках. На корректность вычисления он не влияет: backend всё равно строит dependency-order отдельно.

Запрещены:

- ссылка на несуществующую метрику;
- прямая ссылка метрики на саму себя;
- косвенный цикл, например `A → B → C → A`.

Backend всегда проверяет граф зависимостей. Админка дополнительно не предлагает в dropdown очевидные варианты, которые уже создают цикл. Метрику, на которую ссылается другая метрика, нельзя удалить до удаления этих ссылок.

Значения зависимостей берутся из уже рассчитанного `CITY_REPORT_VALUES.VALUES`; ключи метрик передаются SQL как параметры и не интерполируются в запрос.

## Арифметические операции

Над исходным значением метрики доступны:

- сложение;
- вычитание;
- умножение;
- деление;
- процент (`left / right * 100`).

Операнд выбирается как:

- поле города;
- агрегат геометрий;
- другая метрика;
- одна из разрешённых констант.

Для исходного значения константа запрещена, но разрешены поле города, агрегат и другая метрика.

Деление на `0` или `NULL` даёт `NULL`, а не SQL-ошибку.

Строки арифметических операций можно переставлять кнопками `↑/↓`. Перемещается целиком пара `оператор + правый операнд` вместе с её приоритетом. В отличие от перестановки карточек метрик, здесь порядок функционально значим: после перемещения меняются линейное выражение, итоговая ОПЗ и, при необходимости, фактические скобки.

## Приоритет операций, скобки и обратная польская запись

Линейная последовательность `source → operation → operand → ...` имеет явный **уровень приоритета** для каждой операции. Уровень выбирается только из выпадающего списка от `1` до `12`.

Правила:

- чем больше число, тем раньше выполняется операция;
- операции одного уровня выполняются слева направо;
- если `priority` отсутствует в старой конфигурации, сервер использует `1`;
- поэтому старые настройки сохраняют прежнюю строгую left-to-right семантику.

Это позволяет выразить скобки без ручного ввода текста формулы. Например:

```text
A + B × C
```

если `+` имеет приоритет `1`, а `×` — `2`, вычисляется как:

```text
A + (B × C)
```

и преобразуется сервером в ОПЗ:

```text
A B C × +
```

Чтобы получить:

```text
(A + B) × C
```

нужно поставить `+` приоритет `2`, а `×` — `1`. ОПЗ будет:

```text
A B + C ×
```

Более сложный пример:

```text
(A + B) × (C − D)
```

задаётся приоритетами:

```text
A +[2] B ×[1] C −[2] D
```

и превращается в:

```text
A B + C D − ×
```

Перед компиляцией SQL сервер выполняет алгоритм типа shunting-yard и получает однозначную обратную польскую запись. Затем SQL строится уже по стеку ОПЗ. Поэтому порядок операций не зависит от стандартного SQL-приоритета `* / + -`.

Админка под каждой метрикой показывает два read-only представления:

- фактическую формулу со скобками;
- итоговую ОПЗ.

Ссылки на другие метрики в preview отображаются их человекочитаемыми названиями. Перестановка операций немедленно пересобирает оба preview. Саму формулу или ОПЗ вручную редактировать нельзя.

## Почему здесь нет SQL

JSON-конфигурация не компилируется путём подстановки введённых пользователем имён таблиц или колонок.

Сервер имеет фиксированную таблицу соответствий логических полей своим SQL-фрагментам. Аналогично агрегаторы, виды операндов, арифметические операции и уровни приоритета выбираются только из server-owned whitelist. Константы, выбранные `LINE_TYPES.NAME` и ключи зависимых метрик передаются PostgreSQL параметрами.

Таким образом из админки невозможно ввести произвольное SQL-выражение. Для добавления принципиально нового источника данных его сначала нужно реализовать в коде сервера и добавить в каталог.

## Форматирование отдельно от вычисления

Рекомендуется хранить метрики в канонических единицах, а преобразование делать на уровне колонки.

Например:

- длина хранится в метрах;
- площадь — в квадратных метрах;
- население — в людях;
- доля — как `0..1`.

Для каждой metric-колонки таблицы и CSV отдельно выбираются:

- масштаб (`×0.001`, `×0.01`, `×0.1`, `×1`, `×10`, `×100`, `×1000`);
- количество знаков после запятой либо «как рассчитано».

Поэтому одна метрика `network_length_m` может отображаться в публичной таблице как километры, а в CSV — оставаться метрами.

## Пример: выделенные полосы

Канонические метрики:

```text
lane_length_m = SUM(geometry.lane_length_m)
population = city.population
lane_m_per_1000 = SUM(geometry.lane_length_m) / city.population × 1000
```

Существующая конфигурация V014 оставлена совместимой и продолжает напрямую использовать исходные поля. После сохранения через новый конструктор ту же формулу при желании можно собрать через ссылки:

```text
lane_m_per_1000 = metric(lane_length_m) / metric(population) × 1000
```

Публичная таблица:

```text
№ | город | длина ВП (км) | жители (тыс.) | ВП (м/1000 чел.)
```

Форматирование:

- `lane_length_m × 0.001`;
- `population × 0.001`;
- `lane_m_per_1000 × 1`.

Рейтинг: `lane_m_per_1000`, больше — выше.

## Пример: трамвайные системы

Удобнее разделить базовые показатели и производную долю:

```text
network_length_m = SUM(geometry.length_m)
separated_length_m =
    SUM(geometry.length_m WHERE LINE_TYPES.NAME = «Обособленные»)
population = city.population
separation_ratio = metric(separated_length_m) / metric(network_length_m)
```

Публичная таблица:

```text
№ | город | доля обособления | длина сети (км) | население (тыс.чел)
```

Форматирование:

- `separation_ratio × 100`, например `64.7`;
- `network_length_m × 0.001`;
- `population × 0.001`.

Рейтинг: `separation_ratio`, больше — выше.

Если бизнес-тип в исходных данных называется иначе, в конструкторе выбирается его фактический `LINE_TYPES.NAME` из выпадающего списка.

## Публичная таблица

Публичный endpoint:

```text
GET /api/report-config
```

отдаёт только информацию, необходимую UI:

- порядок и тип колонок;
- заголовки;
- metric key для metric-колонок;
- scale/decimals;
- параметры рейтинга.

Сами значения приходят вместе с `/api/cities` в объекте `metrics`. Заголовок таблицы и строки создаются динамически одним и тем же компонентом для desktop/mobile.

## CSV

CSV настраивается независимо от экранной таблицы. Разрешены:

- место;
- город;
- любая расчётная метрика;
- категория города;
- `minx`, `miny`, `maxx`, `maxy`.

Заголовок CSV задаётся отдельно для каждой колонки. Заголовки должны быть уникальны без учёта регистра.

После пересчёта файл сохраняется как обычный статический:

```text
var/public-downloads/bus-lanes.csv
```

и раздаётся по прежнему URL:

```text
/bus-lanes.csv
```

Динамические admin-export endpoint к этому механизму не относятся и сохраняют полный переносимый формат данных.

## Admin API

Получить конструктор, каталог допустимых значений, виды операндов, уровни приоритета и текущие типы линий:

```text
GET /api/admin/report-config
```

Сохранить конфигурацию и пересчитать материализованные значения:

```text
PUT /api/admin/report-config
Content-Type: application/json
```

Оба endpoint защищены тем же Basic Auth, что и остальная admin API. Сохранение запрещено, пока выполняется длительная admin-задача; на уровне БД также используется общий advisory lock изменения данных.
